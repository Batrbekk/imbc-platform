## Changed contract and remaining constraints

The specification explicitly removes malware scanning, quarantine and scan-dependent blocking, including DATA-07 and the corresponding DBML fields. DBML `file_version` no longer contains scan_state or scanned_at. DATA-06 still requires content-based PDF/JPG/PNG/DOCX/XLSX validation and25MB; NFR-09 and GEN-08–10 still require private storage and authorization on uploads, metadata, GET and HEAD. Exact object/version ownership, immutable revision/history pins, purpose/class/tenant checks, audit and purge exclusion remain necessary. Removing malware checks must not turn an unbound Class C upload into a downloadable report or substitute the latest global version for a captured one.

NFR-11 now requires an agreed, evidence-mapped subset of controls rather than all ASVS Level2 or certification. File-type parsing and bounded parser resources remain distinguishable from malware analysis; each extra rejection for encrypted/embedded content needs a documented type-validation basis rather than a claim that removed DATA-07 requires it. MIG-14 requires supplied CSV/XLSX/XLS file-reference-to-BIN mappings; PDF extraction/OCR is excluded and ambiguous matches require logged manual confirmation. These changes do not relax source ownership or permit guessed BINs/dates.

## Concrete migration hazards

1. **Disabling FileScanJob alone strands successful uploads.** FilesService currently writes bytes into S3_BUCKET_QUARANTINE; only the worker copies them to S3_BUCKET_FILES. Reads use the latter. New writes should validate bytes, stage under a random key in the private files bucket, then commit the exact file row and domain binding. Keep confirmed-rollback cleanup and unknown-COMMIT-ack retention. Object-storage success is not a database commit. Org-chart sample activation currently runs only through SCAN_PASSED_HOOKS and must move into the successful registration/binding transaction.

2. **Removing only the central read check leaves business gates and broken SQL.** Current bindings include stage3_content_guard (0015), profile_review_decision_guard (0020), diligence_report_guard (0027), profile_review_unlock_revision_retained (0028), and both site_survey_record_view/operation_seal (0029). AGAR's unpromoted guard has an additional exact-report check. Replace these function bodies in the new migration while preserving every non-scan predicate and native seal. PL/pgSQL dependencies embedded in bodies may fail only at execution, so successful DROP COLUMN or fresh migration syntax is insufficient. Review snapshot capture, Submit/Core, NOT29 retention, DD, Survey eligibility/company/NOT11, saved-history file ACLs and the new AGAR layer all need aligned runtime changes.

3. **Historical receipts are immutable evidence.** Survey seals and saved receipts contain scanState/rejectionReason/canDownload, and API schemas currently require those fields and a passed state. Existing audits, operation hashes and exact before/after JSON must not be rewritten to pretend a scan passed. Add an explicit compatibility decoder/version strategy for historical receipts and idempotent replay; validate their original sealed content before producing any revised public DTO. Never rebuild a replay response from the latest file/version metadata. New operations should seal the new shape, retaining all normalized object/version FKs and actor/transaction checks.

4. **Old stored bytes cannot be inferred from database state.** Some pending objects exist only in the former quarantine bucket; rejected objects may already have been discarded. Before cutover, inventory exact version/key/checksum/size and actual storage presence. Copy recoverable bytes privately with checksum/size verification and retain immutable version IDs. Missing bytes need an explicit reconciliation result; setting every old row to passed neither restores bytes nor reflects the revised contract. Preserve old scan/audit evidence in an immutable migration archive if active columns are dropped. Storage existence is an operational fact, not a replacement malware status.

5. **The UI and derived state require the same release boundary.** Current upload DTOs require pending, readers require passed, editors poll and disable save, and review readers derive file rejection from scan state. Remove those gates while preserving actual SME rejection outcomes and terminal-authority barriers. Survey eligibility removal can change current tier2/selected reports and durable NOT11 state; recompute from the exact current eligible records, retaining expiry/graph/DD gates. Preserve recipient journals, completed broadcasts, generation fencing and pending recovery; explicitly test migration-created eligibility rather than silently replaying historical mail.
