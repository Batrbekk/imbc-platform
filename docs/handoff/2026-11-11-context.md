Передача контекста из рабочей сессии Claude (30.10–11.11.2026) в репозиторий. Читать первым. Всё, что здесь названо фактом, проверено в сессии; непроверенное собрано в разделе 9.

**Решение от 11.11.2026:** дальше двигаемся от материалов Абая — спецификация v1.3 и его модель данных задают, что строим. Наш код и архитектура подстраиваются под них.

## 1. Проект

Платформа IMBC — реестр проверенных казахстанских производителей для операторов нефтегазовых проектов (NCOC, TCO, KPO), самого IMBC и наблюдателей (например, Министерство энергетики). Заказчик — IMBC, исполнитель — Smart Call. Бизнес-аналитик — Абай Жунис (`AZhunis`), его репозиторий `AZhunis/imbc-prototype` — источник спецификации, глоссария, модели данных и прототипа.

Шесть ролей: производитель, SME (в коде `expert`), администратор IMBC, генеральный директор IMBC (`director`), оператор, наблюдатель (`observer`; в нашем коде пока `spectator`).

## 4. Состояние кода

- `main` — каркас (2 коммита): монорепозиторий pnpm + turbo, `apps/api` (NestJS 12: API + BFF, worker, migrate — один образ), `apps/web` (Next.js 16), `packages/contracts`.
- `feat/web-vite-spa` — перевод `apps/web` на React + Vite SPA и shadcn/ui на Base UI, пресет `base-nova` (решение 11.11, §3). Влита в ветку этапа 0 `feat/spec-v1.3-contracts`; `main` не изменён.
- `azure-dev-deployment` — +10 коммитов поверх `main`, развёрнут на dev-стенде. Законченный срез общей авторизации: собственные экраны входа на shadcn/ui (тема Keycloak через Keycloakify), регистрация производителя с очередью писем, OTP, доверенное устройство, ответственность, backchannel logout, лимиты запросов в PostgreSQL, HTTPS через Caddy, реальная почта через Azure Communication Services. По записи в `docs/development-roadmap.md`: 83 теста API (28 интеграционных), 23 contracts, 4 web.
- Dev-стенд, доступы, обслуживание: `docs/deployment/azure-dev.md`; отчёт проверки: `docs/deployment/verification-2026-11-10.md`.
- Предметные кабинеты ролей не реализованы. Каталог и дашборд работают на демо-данных из `catalog_visible`.
- Коннекторов Adata и e-Ondiris в коде нет.

### Схема данных

У нас 49 таблиц (Drizzle, `apps/api/src/database/schema`), в модели Абая — 76. Имена у нас во множественном числе, у Абая — в единственном.

Таблицы Абая без аналога у нас (38): `activity_snapshot_count`, `agar_cdp_record`, `catalog_profile`, `catalog_profile_facet`, `catalog_tier3_product`, `certificate_expiry_notice`, `dictionary_entry_translation`, `due_diligence_check`, `e_ondiris_record`, `equipment_product_line`, `external_check_attempt`, `forecast_import_issue`, `imbc_legacy`, `import_batch`, `import_resolution`, `import_row`, `main_information`, `main_information_oked`, `migration_invitation_run`, `notification`, `notification_rule`, `operator_request_party`, `org_chart_sample`, `personnel`, `personnel_cv`, `policy_rule`, `product_line_identity`, `production`, `production_photo`, `production_process`, `site_survey_request`, `submission_requirement`, `subscription_run`, `technical_requirements_file`, `update_status`, `update_status_event`, `user_session`, `works_with_mark_change`.

Наши таблицы без аналога у Абая (11): `auth_rate_limits`, `auth_security_events`, `auth_sync_state`, `otp_codes`, `revoked_idp_sessions`, `sessions`, `catalog_visible`, `equipment_product_links`, `notifications_sent`, `site_survey_notices`, `tech_spec_files`. Первые шесть — рабочая авторизация, их оставляем. `tech_spec_files` заменяется на `technical_requirements_file`. `catalog_visible` у Абая названа `catalog_profile`.

Главное структурное отличие: у нас скалярные поля секций (основные сведения, персонал, производство) лежат в `section_revisions.data` (jsonb), а отдельные таблицы есть только для списков — контакты, акционеры, продуктовые линии, оборудование. У Абая каждая секция — своя таблица (`main_information`, `personnel`, `production`…), привязанная к `section_revision`.

## 7. Вопросы к Абаю

1. **Стек во фронтенде.** Спецификация 11.1 и бриф v0.5 фиксируют React + Vite SPA и CASL. Решено владельцем 11.11: Vite SPA (ветка `feat/web-vite-spa`). CASL — по-прежнему открыт: права проверяет собственная матрица `POLICY_MATRIX`.
2. **Покрытие Adata.** Из 116 строк IMBC-10 на текущем токене читается меньше половины; таблица учредителя и бенефициара не читается совсем; 9 строк в API нет. Подключаем модули или фиксируем сокращённый список? Подробности — `adata-integration-notes.md`.
3. **Акционеры.** Adata не отдаёт долю и гражданство учредителя, а MAN-21 делает их обязательными и предзаполняемыми. Предзаполняем только имена?
4. **NDA до профиля.** `nda_acceptance.profile_id` обязателен, но галочка ставится при регистрации, а профиль создаётся после установки пароля. Где хранится принятие между этими событиями?
5. **STR и запрос AGAR.** IMBC-25 разрешает запрос только для продукта с STR, но `technical_requirements_file.product_label` — свободный текст без связи с продуктовой линией. По какому ключу сопоставлять?
6. **История due diligence.** `due_diligence_record` — одна запись на профиль, строки проверок заменяются при каждом запуске. DATA-01 требует историю изменений. Храним прошлые запуски?
7. **Авторизация в модели.** В DBML нет хранилища кодов входа (AUTH-03), а `user_account.failed_attempt_count` и `locked_until` дублируют блокировку, которую ведёт Keycloak. Предлагаем оставить наши таблицы авторизации.
8. **Забор e-Ondiris.** API нет; как именно получать «новые и изменённые записи» раз в день и в каком объёме — не описано. В его `todo.md` это задача «Abay & Batyr» к 13.11.
9. **Напоминания о сертификатах.** `certificate_expiry_notice` ключуется версией файла, а по NOT-30 расписание перезапускает и смена одной только даты истечения.
10. **Квота Adata.** Подсказка в демо говорит, что повторный БИН не списывается; 11.11 остаток после запуска уменьшился на 1.

## 8. Предлагаемый порядок

1. Снять вопросы 1 и 2 с Абаем: они влияют на подписываемый текст.
2. Контракты под v1.3: `observer`, `unresponsive`, тир, матрица прав. Миграция БД — expand → contract.
3. Регистрация по MAN-01/MAN-03: три галочки, NDA, момент создания профиля.
4. Дальше — по `docs/development-roadmap.md` (администрирование → производитель → SME → оператор → наблюдатель → директор), приводя схему каждого модуля к модели Абая по мере его реализации, а не одним переносом.

## 10. Открытые пункты перехода Web UI на Vite SPA
