## Expiry, selection and NOT11

`effectiveSurveyState` now returns the summary plus the end of the entire qualifying period: maximum eligible expiry, or null if any eligible record is perpetual. A newer expired/no/unsigned/unreconciled record cannot cancel an older eligible one. The independent tests establish this pure behavior.

There are two different time boundaries. Example: the newest eligible visit expires tomorrow and an older eligible visit is perpetual. The survey generation never ends tomorrow, but the selected report/date must change tomorrow. Scheduling only the overall `effectiveUntil=null` would leave a cached selected report stale. The coordinator accepted this distinction: current company/report reads must reselect eligible evidence, and catalog selection must refresh at the next relevant individual expiry or use fresh selection in its read path. That refresh must not send another NOT11 while any valid record survives. The later generated draft independently read at `/var/folders/m7/4c2_1w4s3_x3btj7st2w2zqm0000gn/T/imbc-survey29-final-draft-m5gsvgos/drizzle/0029_canonical_site_surveys.sql` includes a separate `next_refresh_on` field and index; the scheduling/read behavior remains to be verified.

The proposed durable surveyed generation separated from visibility matches NOT34. The implementation must still prove all transitions: invisible surveyed → visible once; DD hide/show with the same generation → no repeat; another valid record while already surveyed → no repeat; last eligible expiry → no email; reactivation, including the same record → a new generation; an overdue expiry job must not merge an expired old generation with a new one. Dispatcher revalidation must reject stale generations/currently invisible or invalid evidence. Recipients are operator accounts that are not blocked, not merely the currently active subset; no manufacturer, IMBC or observer recipients.
