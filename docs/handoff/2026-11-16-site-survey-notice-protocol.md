## Implemented protocol

- Effective Survey generations are independent of catalogue visibility. An outbox's trigger record is historical provenance. A currently eligible older/perpetual report may support the same generation after the original trigger ends.
- The worker's minute schedule uses the PostgreSQL Asia/Almaty day and catches the earliest report expiry, stale Survey truth and incomplete outbox entries independently of catalogue visibility. The shared production projection writer re-derives the exact Verified/DD/revision graph before dispatch.
- SQL0030 introduces `dispatch_id`, `notification_job_id`, `resolved_at`, `last_outcome` and publication `last_checked_at`. States are pending/queued/completed/obsolete. Old queued marks have no durable job token and become pending without inventing sent mail. Event identity, terminal outcomes and nondecreasing generations are guarded in SQL.
- A pending valid visible generation queues one strictly scoped IDs/codes-only NOT-11 job and updates its dispatch token in the same `withQueueTransaction`. A disabled/misconfigured rule or denied operator policy defers it without creating a stream of disposable queue jobs.
- Existing created/retry/active queue jobs retain ownership. A missing/failed/completed-but-unacknowledged job is recovered under the same generation/event key with a new fenced dispatch token. A superseded worker cannot complete or send for the replacement token. Old/ineligible generations are silently obsolete; DD hide/show alone does not create a new Survey event.
- Audience policy: each incomplete delivery attempt resolves the current eligible operator accounts; a completed event has no historical backfill for later accounts. Role must actually be operator, organisation type operator and state not blocked; invited/inactive are included. Current email and locale are checked again before sending. An operator moved to another operator organisation remains eligible; a foreign type/role or blocked account is excluded.
- Each recipient has an independent top-level `MailService.sendOnceGuarded` transaction. Lock order is account → current organisation → manufacturer profile → release policy predicate → exact selected file object/version. After the locks, current generation, ANY eligible evidence and canonical public visibility are rechecked immediately before SMTP. A selected-report change during this boundary defers for a fresh attempt.
- A zero-argument SECURITY DEFINER helper with a fixed search path locks the complete policy/notification-rule tables in SHARE mode. Its PUBLIC execute privilege is revoked; runtime receives only helper EXECUTE while policy tables remain SELECT-only. The lock blocks an inserted deny condition as well as updates/deletes through this recipient's SMTP transaction.
- Each accepted address commits its own sent journal. Partial success survives failures of later recipients. Retry sends only addresses without committed journals. A hidden current event is pending; restoration resumes remaining delivery. Aggregate completion/queue acknowledgement failure is recovered by the same stable event/address dedup keys.
- NOT-11 uses EN/RU/KK text and an authenticated company-page link, with no signed URL, file attachment or Class C survey details. The generic renderer refuses NOT-11; only the specialized validated worker route sends it.
- Recovery returns safe counters into pg-boss output and logs sanitized per-candidate failure summaries. Deferred/failed reasons remain inspectable in outbox metadata; no notification inbox is introduced.
