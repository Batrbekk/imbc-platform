# Этап 3 «Профиль производителя» — карта частей

Редакция от 14.11.2026. Подробный план пишется на каждую часть перед её началом, с учётом итогов предыдущей; полностью написан только план части 3а — `docs/superpowers/plans/2026-11-14-stage-3a-profile-foundation.md`. Основание — `docs/development-roadmap.md`, «Этап 3»; спецификация v1.3; DBML.

## Почему три части

Этап — 38 требований, восемь секций, загрузки файлов, полнота, отправка и все состояния профиля, плюс остатки этапа 2, которые надо закрыть до открытия загрузок. Одним планом это 25–30 задач — вдвое больше предела (10–12), и ни одна поставка на стенд не была бы возможна до конца. Три части идут по естественным границам: **до загрузок** (основа и первые секции без файлов), **с загрузками** (остальные пять секций), **отправка и состояния** (переходы статусов, которые опираются на все восемь секций). Каждая выкатывается отдельно и даёт владельцу видимый шаг.

| Часть | Что видно на стенде после выката | Поставки | Зависит от |
|---|---|---|---|
| **3а** основа профиля | обзор профиля из восьми разделов с полнотой и «чего не хватает»; производитель заполняет и сохраняет «Основные сведения», «Контакты», «Акционеры»; отказ загрузки документа под паролем и PDF с вложением с понятной причиной | R1 — contract этапа 2 (`0011`); R2 — `0012`–`0015` и код части | этап 2 на стенде |
| **3б** секции с файлами | производитель загружает файлы и заполняет все восемь разделов: «Персонал», «Продукты», «Производство», «Сертификаты», «Документы», выписка e-Ondiris; видит статус каждого документа и сертификата; профиль доходит до 100 % | один выкат, без contract | 3а выкачена (R2) |
| **3в** отправка и состояния | отправка на проверку с подтверждением достоверности, блокировка, разблокировка, возврат с комментариями, pending changes у верифицированного профиля; решения SME — тестовой командой; первый сквозной сценарий в браузере | выкат части; отдельным релизом — contract этапа 3 | 3б выкачена |

## Часть 3а — основа профиля (план написан)

**Цель.** Закрыть остатки этапа 2 до открытия загрузок и перевести профиль на модель DBML; первые три секции без файлов.

**Требования.** GEN-11; MAN-04, MAN-09–11, MAN-13–15, MAN-21, MAN-22; MAN-40, MAN-41, MAN-43, MAN-46 — частично (сохранение, полнота, правило блокировки, состояние секции); DATA-01 (триггеры, copy-on-write); остатки этапа 2 — GEN-09, DATA-04, DATA-06, DATA-07, NFR-06, NOT-18.

**Задачи.** 1 — релиз contract этапа 2 `0011` (opus, ревью); 2 — приём DOCX/XLSX: вложенные пакеты, записи вне каталога, документы под паролем, инструмент `check-upload` (opus, ревью); 3 — PDF: вложения, пароль, причина отказа скана (opus, ревью); 4 — предел одновременных загрузок (opus, ревью); 5 — модель данных DBML `0013`–`0015` (opus, ревью); 6 — ядро секций (opus, ревью); 7 — правило чтения файла по записи-владельцу, внешние ключи справочников (opus, ревью); 8 — API «Основные сведения» с источником значения (opus, ревью); 9 — API «Контакты» и «Акционеры» (sonnet, ревью); 10 — обзор профиля, экран раздела, форма «Основные сведения» (sonnet); 11 — формы «Контакты» и «Акционеры» (sonnet); 12 — документы и приёмка (sonnet).

## Часть 3б — секции с файлами

**Цель.** Производитель загружает файлы и заполняет оставшиеся пять секций; профиль может дойти до 100 %.

**Требования.** MAN-17–20; MAN-23, MAN-24; MAN-26–32; MAN-33–36; MAN-37–39; MAN-46 (статусы документов и сертификатов); MAN-41 (полнота пяти секций); MAN-40 (все секции); GEN-09 (привязка файла к записи); DATA-05–07 на загрузках производителя; MAN-12 — выписка (необязательный файл).

**Задачи (по строке).**
1. Загрузка файла производителем: `POST /api/v1/profiles/own/files` (поле `purpose` из `MANUFACTURER_FILE_PURPOSES`) — непривязанный `file_object` своей организации; замена — новая версия того же файла (MAN-36); ссылка на файл в разделе — только на свой файл подходящего назначения; файл замороженной редакции — версия, загруженная до `submitted_at`; задание очистки непривязанных файлов (срок — в плане части); ссылки на файл в конвертах разделов (`fileId`, номер версии, имя, размер, тип, состояние скана, причина отказа).
2. API «Персонал» (MAN-17–20): три категории и итог, иностранцы на руководящих должностях, оргструктура (обязательна), CV; ссылка на образец `/api/v1/org-chart-sample/current/content`.
3. API «Продукты» (MAN-23, MAN-24): линии с устойчивой идентичностью, названия en и ru, группа A–E и тип (тип — дочерний группы), ТН ВЭД и КПВЭД из справочников с ведущими нулями, мощность числом и единицей, доля местного содержания, локализация, сертификат соответствия, заметка (вопрос 7); линия не из ручного ввода не правится и не удаляется (значения — этап 4б).
4. API «Производство» (MAN-26–32): необязательная секция; площадь, процессы, цеха, загрузка 0–100, оборудование со ссылками на идентичности линий, фото.
5. API «Сертификаты» (MAN-33–36): тип (обязательные, Others, Other с названием), номер, орган, даты (срок необязателен), файл; статусы uploaded / missing / expired (истечение — по дате Алматы); полнота — каждый обязательный тип с файлом (MAN-35, текущий список ADM-09; снимок при отправке — 3в).
6. API «Документы» (MAN-37–39): свидетельство и устав, лицензии или заявление «лицензия не требуется», прочие типы; учредительные документы по типу компании — по ответу на вопрос 8.
7. Web: слот файла (загрузка, «Проверяется антивирусом» с опросом, причина отказа, замена с историей версий, скачивание) — компонент реестра (`attachment`, если подходит) — и форма «Персонал», выписка в «Основных сведениях».
8. Web: формы «Продукты» и «Производство».
9. Web: формы «Сертификаты» и «Документы»; статусы документов и сертификатов на обзоре (MAN-46).
10. Документы, runbook, приёмка; вживую — настоящий файл 20–25 МБ через Caddy, карантин → рабочий бакет на RustFS стенда, ClamAV.

**Зависимости.** 3а выкачена; корпус `check-upload` прогнан и решение по `entries_gap` принято (3а, расхождение 3). Решить в плане части: срок очистки непривязанных файлов; допустимые типы фото (только JPG и PNG?); поведение линии из реестра в триггере неизменяемости (суточный забор этапа 4б обновляет линию — новая редакция или исключение в триггере).

## Часть 3в — отправка и состояния

**Цель.** Производитель отправляет профиль, видит блокировку, разблокирует, исправляет возвращённое и меняет верифицированное; решения SME до этапа 5 подставляет тестовая команда.

**Требования.** MAN-41 (100 % как условие и список недостающего), MAN-42, MAN-43, MAN-44, MAN-45, MAN-46 (полностью); ADM-09 (снимок `submission_requirement`); DATA-01 (приёмка: отправленная редакция не изменяется); GEN-11 (приёмка этапа).

**Задачи (по строке).**
1. Таблицы DBML `review_assignment`, `review_decision` (expand: нужны тестовой команде и экрану возврата; поведение SME — этап 5) и снимок обязательных типов при отправке (`submission_requirement`, ADM-09).
2. Отправка: полнота 100 %, подтверждение достоверности (`accuracy_confirmed_at`), заморозка рабочих редакций, указатели `pending_revision_id`, статус Submitted, запись очереди с датой получения (REV-04); NOT-04 — этап 5.
3. Разблокировка (MAN-43): в Draft или в Verified с pending changes, решения по нетронутым секциям сохраняются, следующая отправка — тому же SME; NOT-10 — этап 5.
4. Возврат (MAN-44): отклонённые секции, документы и сертификаты с комментарием SME; верифицированное и нетронутое остаётся верифицированным.
5. Pending changes (MAN-45): правка Verified создаёт ожидающие изменения; «Отправить изменения» уходит только с изменёнными секциями; профиль остаётся Verified; проекция не меняется.
6. Тестовая команда решений SME (см. ниже).
7. Web: отправка (диалог подтверждения и список недостающего), блокировка, разблокировка, возврат с комментариями, pending changes; статусы везде (MAN-46).
8. Сквозной сценарий в браузере (см. ниже).
9. Contract этапа 3 — отдельный релиз: удаление скелета профиля (`profile_sections`, `section_revisions`, `contacts`, `shareholders`, `product_lines`, `equipment_items`, `equipment_product_links`, `certificates`, `documents`, `review_assignments`, `review_decisions`), представления `manufacturer_profiles`, типов `profile_section`, `document_status`, `contact_role`, значения `superseded`; задание `certificate-expiry` переводится на `certificate` или выключается до этапа 7.
10. Документы, приёмка этапа 3 целиком (roadmap, «Приёмка»).

**Тестовая команда решений SME (предложение).** Скрипт в образе API `node dist/tools/review-simulate.js --bin <БИН> --verify-all | --return <раздел>=<комментарий> …`: запускается только через `docker compose exec` на стенде и только при `SEED_DEMO=true` (иначе отказ); пишет `review_assignment` и `review_decision` от демо-SME `expert@imbc.local`, аудит с `origin: 'test_command'`. HTTP-маршрута нет — дыры в правах нет: выполнить её может только тот, у кого есть доступ к VM. Цена ошибки малая: этап 5 заменит её экраном SME, скрипт остаётся для тестов или удаляется.

**Сквозной сценарий в браузере — два варианта.**
- **Playwright в репозитории** (`apps/e2e`, `@playwright/test`, Chromium): `pnpm e2e` против локального стенда (демо-вход с фиксированным кодом, ссылка установки пароля — из API Mailpit). Цена: новая зависимость и примерно одна задача на настройку и первый сценарий; селекторы надо поддерживать; в CI не встаёт, пока GitHub Actions заблокирован, — запуск локальный, в конвейер — на этапе 10. Даёт повторяемую проверку и основу для сценариев шести ролей (roadmap §3.4, этап 10).
- **Сценарий контроллера** на локальном стенде через браузер, записью в `docs/deployment/verification-<дата>.md`. Цена: ноль в репозитории; не повторяется сам и не ловит регрессию.
- Предложение: Playwright в 3в, запуск локальный; осмотр 1280 и 390 px остаётся за контроллером. Решает владелец.

## Границы с другими этапами

- **4б:** значения из e-Ondiris и Adata в разделах (таблица `section_field_source` и подтверждение готовы с 3а), MAN-12 (зарегистрирован, дата, ОКЭД реестра), линии из реестра (MAN-25). Сопоставление полей Adata (`PREFILL_FIELDS`: `legal_name` → `name_ru`, `activity` → `oked`, `company_email` → `contact_email`) — план 4б.
- **5:** письма NOT-04, NOT-05, NOT-10; экраны SME (REV-05–REV-09) и чтение профиля SME и директором через интерфейс; проекция `catalog_profile`.
- **6:** файлы видимого профиля для оператора и наблюдателя — правило `manufacturerFileRule` по верифицированной редакции.
- **7:** напоминания о сертификатах, статус актуальности, подтверждение секций (UPD-05).
