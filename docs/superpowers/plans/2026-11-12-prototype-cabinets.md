# Кабинеты ролей: прототип на уровне интерфейса — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** на dev-стенде у каждой роли свой кабинет с разделами по спецификации v1.3, по которым можно пройти на показе: формы открываются, действия меняют состояние, роли видят последствия действий друг друга. Сервера за этими разделами нет — данные вымышленные и живут в браузере.

**Почему так.** Настоящие разделы — это этапы 1–9 roadmap. Владелец 12.11.2026 попросил: «на всех аккаунтах нужны разные кабинеты… реальные кабинеты только на уровне фронта, чтобы на демо они могли потыкать». Сейчас оператор, наблюдатель и директор видят одно и то же (дашборд и каталог), потому что построена только общая часть их прав; отличия — в строках таблицы раздела 4, которых в интерфейсе ещё нет.

**Architecture:** слой `apps/web/src/prototype/` поверх готовой оболочки. Модуль роли отдаёт пункты меню и маршруты через общий реестр; оболочка и роутер подключают реестр только при сборке с `VITE_PROTOTYPE_CABINETS=true`. Данные — типизированные наборы в `prototype/data`, состояние — одно хранилище в `localStorage`, поэтому действие одной роли видно другой роли в том же браузере. Готовые экраны (дашборд, каталог, страница компании, свой профиль, очередь, аккаунты) и сервер не меняются.

**Tech Stack:** React 19, React Router 8, TypeScript, shadcn/ui на Base UI (`base-nova`), use-intl (только `useMe`/локаль), vitest + Testing Library.

**Spec:** `docs/analyst/2026-11-11/specification-v1.3.md` — раздел 4 (таблица прав) и разделы ролей: 5 (производитель), 6 (сотрудники IMBC), 7 (оператор), 8.2 (уведомления), 8.4 (аудит), 9.1–9.2 (записи и колонки выгрузки).

## Global Constraints

- Ветка `demo/prototype-cabinets` от `feat/spec-v1.3-contracts`. В `main` и в PR этапа 0 слой не попадает без решения владельца; на dev-стенд выкатывается с этой ветки.
- Только интерфейс: экраны и правила кабинетов живут в web. Нет правок матрицы прав и рабочих таблиц. Экраны прототипа не обращаются к `/api/v1`; из сервера берётся только сеанс (`useMe`: роль, язык). Adata не вызывается никогда: «запуск проверки» — локальная имитация. **Изменение 12.11 (владелец: «данные должны же в бд жить, потому что как я им предоставлю демо»):** состояние прототипа хранится на сервере одним документом и общее для всех пользователей и браузеров стенда — задача 8; к серверу обращается только общее хранилище слоя, экраны кабинетов по-прежнему нет.
- Флаг сборки `VITE_PROTOTYPE_CABINETS`, по умолчанию `false`. Без флага нет ни пунктов меню, ни маршрутов, ни кода прототипа в сборке. Флаг включён для dev-стенда (`compose.azure.yaml`) и задаётся переменной `PROTOTYPE_CABINETS` для локального стенда.
- Всё лежит в `apps/web/src/prototype/**`, тесты — в `apps/web/test/prototype/**`. Модуль роли меняет только свой каталог `prototype/<role>/**` и свои тесты. Общие файлы (реестр, хранилище, данные, общие компоненты, `components/ui`, `package.json`) меняет только задача 1.
- Адреса: `/proto/<role>/<screen>`. Роль сеанса не совпадает с ролью модуля — переход на стартовую страницу роли (`authDestination`).
- Каждая страница прототипа помечена бейджем «Прототип» с пояснением: данные вымышленные, изменения хранятся только в этом браузере. В меню разделы прототипа стоят отдельной группой под готовыми разделами.
- Данные вымышленные: компании — те же двенадцать, что в seed (восемь в каталоге, четыре вне его), люди и адреса — на `.demo.local`, операторы — «Оператор (демо)» и два условных крупных оператора без настоящих названий. Настоящих людей, компаний, документов и адресов нет.
- Тексты на трёх языках. У модуля свой типизированный словарь `{ en, ru, kk }` (`satisfies Record<Locale, …>`): пропущенный ключ не компилируется. Термины — из глоссария (observer, unresponsive, SME, STR, KTRE, e-Ondiris). Казахский — коротко, на проверку носителю.
- Интерфейс — по `apps/web/AGENTS.md`: компоненты только из `src/components/ui`, один `PageTitle` на страницу, даты и числа через `useFormat`, ссылка-кнопка — `<Link className={buttonVariants(...)}>`, состояния «пусто» различимы. Ширина 1280 и 390 px — без горизонтальной прокрутки страницы.
- В начале файла экрана — комментарий со списком ID требований, которые экран показывает; ID существуют в спецификации (`pnpm check:requirements`). Возможности Release 2 (прогноз спроса, STR и KTRE, подписки на выгрузку) помечены бейджем «Release 2».
- Экран показывает ровно то, что роль вправе видеть по таблице раздела 4 и своим требованиям: наблюдатель — без focal point и без действий; оператор — без данных другого оператора (GEN-12); производитель не видит, какой оператор спросил (GEN-11); администратор не видит данных профилей (ADM-06); директор ничего не меняет (GEN-04).
- Конец задачи: `pnpm typecheck && pnpm lint && pnpm test && pnpm build` и `pnpm check:requirements` зелёные; один коммит с ID требований в сообщении; без `git push` и выката.

## Review Focus

1. Сборка без флага не содержит прототипа: нет пунктов меню, маршрут `/proto/...` — «не найдено», в `dist` нет чанков прототипа.
2. Роль не открывает чужой модуль по прямому адресу.
3. Действие одной роли видно другой после смены аккаунта в том же браузере; «Сбросить демо-данные» возвращает исходное состояние.
4. Ни один экран не показывает роли больше, чем разрешает таблица раздела 4.
5. Повреждённое или устаревшее содержимое `localStorage` не роняет приложение: хранилище возвращается к исходным данным.

### Task 8: общее состояние прототипа в базе данных (добавлена 12.11)

**Зачем.** Демо отдают людям заказчика: каждый входит своей ролью со своего компьютера. Состояние в `localStorage` у каждого своё, поэтому оператор на одной машине и SME на другой не видят действий друг друга, а данные живут до очистки браузера. Состояние должно лежать в базе стенда и быть одним на всех.

**Что это и чем не является.** Сервер хранит документ состояния целиком и ничего о нём не знает: правила ролей, проверки и журнал прототипа по-прежнему исполняет web. Это не модули этапов 1–9: рабочих таблиц, серверных прав на разделы кабинетов (GEN-08) и настоящего журнала аудита за прототипом нет. Любой вошедший пользователь стенда читает и перезаписывает весь документ; данные в нём вымышленные, ничего из сеанса в него не попадает. Только при `PROTOTYPE_CABINETS=true`.

**Files:** `packages/contracts/src/prototype.ts` (новый) + `index.ts`; `apps/api/src/modules/prototype/prototype.{controller,service,module}.ts` (новые), `apps/api/src/app.module.ts`, `apps/api/src/config/env.ts`, `apps/api/src/database/prototype-store.ts` (новый) и вызов в `apps/api/src/database/migrate.ts`; `apps/api/test/prototype.http.test.ts`, `prototype.integration.test.ts` (новые); `apps/web/src/prototype/{store.ts,remote.ts (новый),gate.tsx,labels.ts,README.md}`, `apps/web/test/prototype/{remote.test.tsx (новый),support.tsx}`; `compose.yaml`, `compose.azure.yaml`; `apps/web/AGENTS.md`, `README.md` (по абзацу).

**Interfaces.**

- Таблица `prototype_state (id text primary key, version bigint not null, state jsonb not null, updated_at timestamptz not null)`, одна строка `id = 'default'`. Создаётся заданием `migrate` командой `CREATE TABLE IF NOT EXISTS` только при `PROTOTYPE_CABINETS=true`, до выдачи прав роли приложения. В журнал миграций Drizzle и в схему `apps/api/src/database/schema` не входит: слой одноразовый и не должен занимать номер миграции (следующий номер — релиз contract этапа 1).
- `GET /api/v1/prototype/state` → `{ version: number, state: object | null }`; `PUT /api/v1/prototype/state` с телом `{ baseVersion: number, state: object }` → `200 { version }` либо `409 { version, state }`, если `baseVersion` устарел (сравнение и запись одной командой `UPDATE … WHERE version = $base`; первая запись — `INSERT … ON CONFLICT DO NOTHING` при `baseVersion = 0`). Оба требуют сеанса; роль любая. При выключенном флаге маршрутов нет (404). Тело до 2 МБ; `state` — объект с числовым `schemaVersion`; иначе 400.
- Web: хранилище остаётся источником для экранов (`useProto`, `useProtoUpdate`, `resetProto` — сигнатуры не меняются). Режим определяется при открытии кабинета: `GET` ответил 200 — общий режим, 404 — локальный (как сейчас; в нём идут все тесты кабинетов). Общий режим: начальная загрузка с сервера (пустой сервер — записать исходные данные); правка применяется сразу и отправляется `PUT`; при 409 берётся состояние сервера, рецепт применяется к нему заново и запись повторяется (до трёх раз, затем сообщение и состояние сервера); чужие правки подтягиваются опросом раз в несколько секунд и при возврате на вкладку; «Сбросить демо-данные» записывает исходные данные для всех. `localStorage` остаётся копией для мгновенной отрисовки.
