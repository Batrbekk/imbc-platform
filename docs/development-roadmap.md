«Делаем по спецификации Абая» означает пять правил:

1. **Объём — только из спецификации.** Требование читаем в тексте, а не по памяти. Код, тесты и коммиты ссылаются на ID (`MAN-25`, `UPD-04`). Чего в спецификации нет, того в фазе 1 нет.
2. **Термины и идентификаторы — из глоссария и DBML.** Observer, unresponsive, SME, STR, KTRE, e-Ondiris; имена таблиц, колонок и значений перечислений — как у Абая.
3. **Модель данных — таблицы и колонки DBML.** Отступление допускается только записанное и согласованное с Абаем (раздел 4.2).
4. **Где код расходится со спецификацией, меняется код.**
5. **Где спецификация расходится с реальностью или сама с собой, молча не решаем.** Вопрос уходит Абаю (раздел 9). До ответа действует значение по умолчанию, записанное в плане этапа.

Спецификация имеет статус «draft for sign-off». На встрече 11 ноября решено ждать весь отзыв IMBC сразу, поэтому текст ещё изменится. Порядок при новой редакции: новый снимок в `docs/analyst/<дата>/`, сверка по ID требований, правка этого плана и карты требований (раздел 11), затем правка затронутых этапов.

## 3. Как ведём разработку

### 3.1. Цикл этапа

1. Перечитать разделы спецификации этапа в тексте. Проверить, не вышла ли у Абая новая редакция.
2. Написать подробный план этапа: файлы, миграции, тесты, приёмочный сценарий. Владелец подтверждает план.
3. Реализовать вертикальными срезами в ветке `feat/<этап>-<срез>`: тест → код → проверка. Коммит на срез, с ID требований.
4. Проверить: `pnpm typecheck && pnpm test && pnpm build`, интеграционные тесты на PostgreSQL 18, тесты прав. Те же проверки с этапа 0 выполняет сборочный конвейер на каждый коммит ветки.
5. Провести независимое ревью ветки.
6. Обновить README, этот план и `docs/handoff/`.
7. По команде владельца выкатить на dev-стенд и пройти приёмочный сценарий этапа демо-ролями. Результат записать в `docs/deployment/verification-<дата>.md`.

Без команды владельца ничего не публикуется и не развёртывается.

### 3.2. Готовность среза

- Каждое требование среза закрыто тестом, демонстрацией или обзором (ACC-01); способ записан в карте требований.
- Права проверяет сервер по матрице `packages/contracts/src/policy.ts`. На каждое новое действие есть тест разрешённого и отклонённого запроса (GEN-08, NFR-12). Отказ пишется в аудит.
- Каждое действие пишет запись аудита: кто, организация, время, объект, что изменилось (AUD-01).
- Все пользовательские тексты есть на казахском, русском и английском; наборы ключей совпадают. Исходный язык — английский (LANG-02).
- Миграция совместима с предыдущей версией приложения: expand → migrate → contract (NFR-06).
- OpenAPI соответствует маршрутам.
- В логах и ошибках нет секретов и URL Adata.

### 3.3. Правила данных и интеграций

- **Проекция.** Каталог, страница компании, выгрузки, pull API и дашборд читают только проекцию видимых профилей.
- **Редакции.** Отправленная и верифицированная редакция секции не перезаписывается (DATA-01). Оператор видит верифицированные значения.
- **Коды.** БИН, ОКЭД, ТН ВЭД, КПВЭД, ЕНС ТРУ хранятся текстом (DATA-03). Многозначные поля — отдельными строками (DATA-02).
- **Файлы.** Файл недоступен, пока не прошёл антивирус; отдаётся только после проверки прав записи-владельца (DATA-07, GEN-09).
- **Время.** Даты, сроки и расписания считаются по Asia/Almaty (DATA-08).
- **Внешние сервисы.** Только через коннектор и только из worker. В тестах — заглушка на записанных ответах. Реальный вызов Adata расходует квоту заказчика и делается по прямой команде владельца.
- **Почта.** Автоматические тесты пишут на адреса `.local`; они остаются в Mailpit.

### Этап А. Общий вход — сделан

Требования: AUTH-01–05, AUTH-08–10; MAN-02; NOT-01–03; LANG-01.

Реализовано:

- Вход через OIDC Code + PKCE и BFF-сеанс, пароль остаётся у провайдера идентификации. Все экраны авторизации — собственная тема IMBC на shadcn/ui с переводами kk/ru/en. Стандартные формы Keycloak пользователю не показываются.
- Саморегистрация производителя с проверкой БИН и одним аккаунтом на БИН. Письмо ставится в очередь в той же транзакции. Неудачное удаление пользователя IdP повторяется через `cleanup-identity`.
- Установка и восстановление пароля по почте, ссылка действует 72 часа.
- Шестизначный код на новом устройстве: 10 минут, пять попыток, пауза между отправками. Доверенное устройство хранится 30 дней.
- Принятие ответственности с версией текста. До кода и принятия ответственности рабочие API закрыты.
- Сеанс: 30 минут бездействия, 12 часов от аутентификации. Десять неудачных входов блокируют аккаунт на 15 минут.
- Проверка Origin, ограничения частоты в PostgreSQL, подписанный backchannel logout, отзыв сеансов при смене пароля.
- На dev для демо-аккаунтов действует фиксированный код; порядок — в [runbook](deployment/azure-dev.md#демо-аккаунты-с-фиксированным-кодом).

Автоматические проверки на 10 ноября 2026 года: API — 83 теста, из них 28 интеграционных на PostgreSQL 18; contracts — 23; web — 4. Результаты проверки стенда — в [отчёте от 10.11.2026](deployment/verification-2026-11-10.md).

Критерии приёмки:

1. На настоящем почтовом адресе проходят регистрация → письмо → установка пароля → код → ответственность → стартовая страница роли.
2. Восстановление пароля доступно с экрана входа. Новый пароль работает, старый нет; повторное использование и истечение ссылки дают понятное объяснение.
3. Ошибка почты не теряет регистрацию; письмо остаётся в очереди.
4. Неверный, просроченный, заменённый и использованный код отклоняются. Параллельные запросы не обходят пять попыток и паузу.
5. После смены пароля сеансы и доверие к устройствам на старых учётных данных прекращаются. Отзыв IdP-сеанса закрывает сеансы BFF.
6. Недоступность почты не задерживает отзыв доступа. Неподписанное, чужое, просроченное или повторное уведомление об отзыве не нарушает чужие сеансы.
7. Все шесть ролей проходят вход, выход и повторный вход. Внешний `returnTo` не принимается.
8. Ошибки сети, повторная отправка и смена аккаунта доступны с клавиатуры и на телефоне.
9. Демо-роли проходят вход с фиксированным кодом без письма; аккаунт вне списка получает почтовый код.

### Этап 3. Профиль производителя

**Цель.** Производитель заполняет профиль из восьми секций, отправляет на проверку, исправляет возвращённое и меняет верифицированное.

**Требования.** GEN-11; MAN-04, MAN-09–11, MAN-13–15, MAN-17–24, MAN-26–46; DATA-01.

**Данные.** По DBML: `manufacturer_profile`, `profile_section`, `section_revision`, `submission_requirement`, `main_information`, `main_information_oked`, `contact`, `personnel`, `personnel_cv`, `shareholder`, `product_line_identity`, `product_line`, `production`, `production_process`, `production_photo`, `equipment_item`, `equipment_product_line`, `certificate`, `document`. Скалярные поля секций переезжают из `section_revisions.data` в таблицы секций. У полей, которые предзаполняются из e-Ondiris и Adata, хранятся источник, исходное значение и отметка подтверждения. У продуктовой линии хранится признак «из реестра» (`product_line.source`).

**Работы.**

- Секции: основные сведения, контакты, персонал, акционеры, продукты, производство, сертификаты, документы. Секция сохраняется в любой момент.
- Контакты: не меньше трёх, одна роль у каждого, ровно один focal point; контакт с повторяющимся email или телефоном не сохраняется (MAN-13).
- Продукты: линия с ТН ВЭД из справочника, мощность числом и единицей; оборудование ссылается на устойчивую идентичность линии. Линия с признаком «из реестра» не редактируется и не удаляется.
- Предзаполняемое поле показывает источник и ждёт подтверждения. Сами значения и линии из реестра приходят на этапе 4б.
- Сертификаты: обязательные типы и Others, включая Other с названием; срок действия необязателен. Документы: свидетельство, устав, лицензии или заявление «лицензия не требуется».
- Полнота: секция — доля заполненных обязательных полей и файлов; профиль — среднее семи секций без производства. Отправка доступна при 100 % и подтверждении достоверности.
- Состояния: блокировка на проверке; разблокировка возвращает в Draft или в Verified с pending changes; возврат показывает отклонённые секции с комментарием; правка верифицированного профиля создаёт pending changes.
- БИН и почта-логин не редактируются.
- До этапа 5 решения SME подставляет тестовая команда.
- Первый сквозной сценарий в браузере.
- Готовая основа: свой профиль только для чтения (`/profile`) — статус, заполненность, статус актуальности и тир (GEN-11).

**Приёмка.** Производитель заполняет профиль, загружает документы, видит, чего не хватает, отправляет и исправляет возвращённое. После принятия изменений различает рабочие, ожидающие и верифицированные значения. Аккаунт одной компании не читает и не меняет профиль другой ни через интерфейс, ни через API. Отправленная редакция не изменяется.

**Вопросы.** 6, 7, 8.

### Этап 4а. Внешние источники: копия e-Ondiris, коннектор Adata, каталог проверок

**Цель.** Данные двух источников доступны платформе по БИН, а результат due diligence считается по каталогу проверок. Экраны профиля для этого не нужны, поэтому этап идёт параллельно этапам 1 и 3.

**Требования.** IMBC-10–12, IMBC-14; EXT-01, EXT-02, EXT-04, EXT-05.

**Данные.** `e_ondiris_record`, `external_check`, `external_check_attempt`, `due_diligence_record`, `due_diligence_check`.

**Работы.**

- **Копия e-Ondiris.** Суточное задание забирает новые и изменённые записи; изменение определяется по хешу записи. Из 27 полей реестра храним 21: штрихкод, АГСК-3, NTIN, комментарий и источник данных не сохраняются.
- **Коннектор Adata.** Задание worker: запрос, опрос раз в 5–10 секунд до 90 секунд. Токен из `ADATA_API_TOKEN`; URL с токеном не попадает в логи. Учёт квоты 3 000 БИН в месяц; запросы идут пакетами с ограничением частоты.
- **Каталог проверок.** 116 строк IMBC-10 как данные: группа, строка, тип, поле источника. Метки clear, finding, shown only, no answer; отсутствующая строка не создаётся. Результат green, amber или red по IMBC-11 и IMBC-14. Запуск по БИН записывает результат и строки проверки. Части отчёта, которые не являются проверками, не запрашиваются и не хранятся (IMBC-12).
- **Заглушки** остальных коннекторов: четыре случая — green, amber, red, недоступен; результат помечен как тестовые данные.

**Приёмка.** Повторный суточный забор не создаёт дублей и обновляет изменённые записи. Сбой суточного забора, недоступность сервиса и ответ «модуль не подключён» не становятся находкой. На наборе строк из образца отчёта в спецификации результат — amber. Ноль налогов за последний год даёт red. Заглушки показывают четыре случая и помечены как тестовые данные.

**Вводные.** Решение IMBC по модулям Adata. Способ забора e-Ondiris: открытый адрес реестра по БИН или файл, который IMBC скачивает по вторникам.

**Вопросы.** 9, 10, 12, 13, 14, 16.

### Этап 4б. Предзаполнение профиля и запуск due diligence

**Цель.** Профиль предзаполняется из копии e-Ondiris и из Adata; due diligence запускается при создании профиля и повторяется раз в квартал.

**Требования.** MAN-06–08, MAN-12, MAN-25; IMBC-07.

**Данные.** Новых таблиц нет. Заполняются источник и подтверждение полей и линии с признаком «из реестра», заведённые на этапе 3; линия получает ссылку на запись копии e-Ondiris.

**Работы.**

- При создании профиля одно чтение Adata даёт и предзаполнение, и первый запуск due diligence. Повтор — раз в квартал от последней проверки. БИН брошенной регистрации не запрашивается (IMBC-07).
- Название, вид деятельности, телефон и контактный email: e-Ondiris, затем Adata, затем вручную (MAN-06). Юридический адрес, руководитель, дата регистрации, акционеры, правовая форма — Adata (MAN-07). Численность вводит производитель.
- Каждое предзаполненное значение производитель подтверждает или исправляет (MAN-07). В прототипе Абая неподтверждённое поле не считается заполненным — берём то же правило. Позднее чтение не заменяет сохранённое значение.
- Unified Register: «зарегистрирован», если копия вернула хотя бы один продукт; дата первого включения — самая ранняя среди продуктов; ОКЭД реестра показан рядом с выбранными кодами и не заменяет их (MAN-12).
- Продукты из реестра: одна запись — одна линия. Линия не редактируется и не удаляется; добавить вторую линию с тем же названием и кодом ТН ВЭД нельзя. Если суточный забор принёс продукт, который производитель уже добавил, остаётся линия из реестра. Суточный забор обновляет такую линию. У линии, добавленной вручную, ДВЦ равна 0 (MAN-25).

**Приёмка.** Брошенная регистрация не расходует квоту. Открытие профиля не вызывает Adata и e-Ondiris. Значение, сохранённое производителем, не заменяется поздним чтением. Линию из реестра нельзя изменить, удалить или продублировать. Если копия не вернула продуктов, производитель добавляет линии сам.

**Вопросы.** 6, 11, 15.

Результат red держит профиль вне выдачи оператора, пока SME не поставит green или amber. Письмо об обследовании уходит один раз и только по видимому профилю.

- Поиск: общие и расширенные фильтры OPR-02 и OPR-03; между фильтрами AND, внутри OR; по сертификатам — действующие, если оператор не выбрал иначе. SME и директор ищут по всем профилям.
- Страница компании: верифицированные значения, документы, тир, продукты tier 3, отметка «изменения на проверке». Скачивание страницы одним PDF.
- Наблюдатель: та же страница без focal point и списка tier 3; без выгрузок, подписок, pull API и записи.
- Дашборд: число производителей, карта по регионам, группы A–E, обследование, тир, Unified Register, три статуса актуальности. Показатель открывает список с фильтром.
- Выгрузка XLSX и CSV: одна строка на продуктовую линию, колонки DATA-09, правила DATA-10–12, исключения DATA-13.
- Отметки works-with и визитов, которые подтверждает SME. Другим операторам виден только счётчик.
- Заметки оператора: своя организация, SME и директор. Запрос к IMBC. Запрос производителю с одним ответом; производитель не узнаёт, кто спросил.
- Pull API: только чтение, набор полей страницы компании, права оператора; ключ выдаёт и отзывает администратор.
- Директор: все профили и записи IMBC только на чтение.
- Нагрузочный тест поиска и страницы компании.
- Готовая основа (этап 0 и демо): тир 1 и 2 в фильтре, результатах и на дашборде; стартовая страница — дашборд; право `focal_point.read`, без которого наблюдатель не получает focal point; страница компании только для чтения (`/companies/:profileId`) из проекции.

**Приёмка.** Оператор находит компанию, передаёт ссылку с фильтрами, читает документы, оставляет запись. Невидимые профили, непроверенные правки, записи IMBC и записи другой организации недоступны в интерфейсе, файлах, выгрузках, pull API и прямых запросах. Наблюдатель получает отказ сервера на выгрузку, подписку, pull API и любую запись. Директор ничего не может изменить.

**Вопросы.** 19, 20, 21, 26.

### Этап 7. Актуальность, уведомления, аудит

**Цель.** Квартальный цикл актуализации, полный каталог писем, журнал и снимки активности.

**Требования.** UPD-01–05; REV-10; NOT-06, NOT-12, NOT-15, NOT-16, NOT-30, NOT-31; LANG-02; AUD-01–04; DATA-08.

**Данные.** `update_status`, `update_confirmation`, `update_status_event`, `certificate_expiry_notice`, `activity_snapshot`, `activity_snapshot_count`; `audit_entry` секционируется по месяцам перед продакшеном.

**Работы.**

- Квартал — три календарных месяца от собственной даты профиля. Дата сдвигается подтверждением и принятием изменения SME.
- В дату квартала уходит NOT-12; через семь дней без подтверждения статус outdated. В следующую дату — NOT-15; ещё через семь дней — unresponsive и NOT-16. Verified не снимается, профиль остаётся видимым.
- Не больше 50 писем NOT-12, NOT-15, NOT-16 в день; остальные ждут следующего дня в порядке срока.
- Возврат из unresponsive — подтверждение каждой секции; активным профиль делает последнее.
- Истёкший сертификат переводит active в outdated; замена возвращает active, если причина была только в нём.
- Напоминания о сертификатах за 60, 30, 7 дней и в день истечения; одно письмо получателю в день.
- Полный каталог писем: тексты всех писем лежат в языковых файлах, английский — исходный (LANG-02). Общие правила рассылки заведены на этапе 2.
- Аудит: вход, выход, отказы, смены статусов, решения, принятия NDA, выгрузки, скачивания, открытия страниц компаний. Хранение пять лет, без изменения и удаления.
- Журнал для директора с фильтрами; для администратора — только события аккаунтов. Снимки недели и месяца.

**Приёмка.** Границы семи дней и квартала проверяются управляемым временем. Повтор задания не отправляет второе письмо. Письма сверх 50 уходят на следующий день. Три месяца без входа не двигают квартал.

**Вопросы.** 22.

### Этап 8. Миграция

**Цель.** База IMBC из Excel и файлы обследований перенесены; мигрированные производители приглашены.

**Требования.** ADM-04; NOT-22, NOT-25; MIG-01–15; ACC-03.

**Данные.** `import_batch`, `import_row`, `import_resolution`, `migration_invitation_run`; заполняется `imbc_legacy`.

**Работы.**

- Сопоставление 38 колонок книги с полями платформы; утверждает IMBC.
- Один БИН — один профиль, одна строка — одна продуктовая линия. Значения приводятся к справочникам; несопоставленные сохраняются и помечаются.
- Строки «OUT OF» и «N/A», возможные дубликаты и БИН с неверным контрольным разрядом помечаются, не отбрасываются и не сливаются.
- «Supply to Operators» для NCOC, TCO, KPO становится подтверждёнными отметками works-with. Визиты — записями обследований без файла. Шестнадцать внутренних колонок — отдельными legacy-полями.
- Около 320 PDF обследований привязываются по БИН; остальные — вручную.
- Пробный импорт повторяется без дублей и без писем. Каждый импорт даёт журнал по строкам и отчёт.
- Профили создаются в Draft и скрыты. Due diligence — один раз при импорте, в пределах месячной квоты.
- «Пригласить всех мигрированных» с отчётом о профилях без почты.
- Мигрированный производитель принимает текущую версию NDA при первом входе. Принятие записывается так же, как при регистрации: время, версия, IP (FC-02).

**Приёмка.** Учтено 100 % строк Excel: профиль, продуктовая линия или отклонение с причиной. На выборке не меньше 200 записей расходится меньше 5 % проверенных полей (ACC-03). Мигрированный производитель при первом входе принимает NDA, и принятие записано.

**Вводные.** Финальная книга производителей; доступ к файлам обследований.

### Этап 9. Release 2: прогноз, STR и KTRE, подписки

**Цель.** Верифицированный производитель, принявший NDA, видит прогноз спроса и технические требования; оператор получает выгрузки по расписанию.

**Требования.** FC-01, FC-03–10; IMBC-25; ADM-10, ADM-12–15; OPR-15–18; NOT-09, NOT-17, NOT-35.

**Данные.** `forecast_version`, `forecast_import_issue`, `forecast_line`, `technical_requirements_file`, `export_subscription`, `export_file`, `subscription_run`.

**Работы.**

- Импорт прогноза из XLSX с фиксированным набором колонок; отчёт по строкам; публикация версией.
- Таблица прогноза: поиск, фильтры по колонкам, префикс ТН ВЭД. Без скачивания и печати.
- Раздел технических требований: товарная группа → продукт → STR или KTRE в просмотрщике с масштабом и прокруткой. Без скачивания и печати. Из строки прогноза файл не открывается.
- Запрос AGAR: верифицированный производитель просит AGAR по продукту, у которого есть STR. Без STR запрос не принимается. Запрос попадает в список SME и письма не отправляет (IMBC-25, развилка Р-6).
- Версии NDA: новая версия закрывает оба раздела до повторного принятия.
- Подписки: название, формат, период; файл со ссылкой в письме, без вложения; файлы за 90 дней; пауза при неактивности аккаунта и предупреждение за 14 дней.

**Приёмка.** Разделы закрыты, пока профиль не Verified и не принята текущая версия NDA. У таблицы нет скачивания; продукт без файла ничего не открывает. Запрос AGAR по продукту без STR отклоняется. Письмо подписки получает только её владелец; неудачный запуск письма не шлёт.

**Вводные.** Полная товарная книга, файлы STR и KTRE, текст NDA.

**Вопросы.** 17, 18, 23, 24.
