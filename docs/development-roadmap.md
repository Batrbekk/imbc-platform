Состояния уже выполненных этапов ниже сохраняют даты их фактических проверок; наличие нового плана не означает реализации или выката. В v1.4 добавлены 16 ID (LPS-01–08, OPR-39–43, MIG-16, ACC-06–07), без удаления прежних ID; одновременно изменилось содержание существующих требований к профилю, источникам, импорту и релизам. Сверка только номеров не проверяет соответствие поведения.

«Делаем по спецификации Абая» означает пять правил:

1. **Объём — только из спецификации.** Требование читаем в тексте, а не по памяти. Код, тесты и коммиты ссылаются на ID (`MAN-25`, `UPD-04`). Чего в спецификации нет, того в фазе 1 нет.
2. **Термины и идентификаторы — из глоссария и DBML.** Observer, unresponsive, SME, STR, KTRE, e-Ondiris; имена таблиц, колонок и значений перечислений — как у Абая.
3. **Модель данных — таблицы и колонки DBML.** Отступление допускается только записанное и согласованное с Абаем (раздел 4.2).
4. **Где код расходится со спецификацией, меняется код.**
5. **Где спецификация расходится с реальностью или сама с собой, молча не решаем.** Неоднозначность фиксируется в плане и внешних вводных. Историческое предложение не считается согласованным ответом; независимая работа продолжается в рамках текущих требований.

Спецификация имеет статус «draft for sign-off». Подпись и полный отзыв IMBC пока не зафиксированы; изменения после новой редакции учитываются до реализации затронутого среза. Порядок при новой редакции: новый снимок в `docs/analyst/<дата>/`, сверка по ID требований, правка этого плана и карты требований (раздел 11), затем правка затронутых этапов.

## 3. Как ведём разработку

### 3.1. Цикл этапа

1. Перечитать разделы спецификации этапа в тексте. Проверить, не вышла ли у Абая новая редакция.
2. Написать подробный план этапа: файлы, миграции, тесты, приёмочный сценарий. Владелец подтверждает план.
3. Реализовать вертикальными срезами в ветке `feat/<этап>-<срез>`: тест → код → проверка. Коммит на срез, с ID требований.
4. Проверить: `pnpm typecheck && pnpm test && pnpm build`, интеграционные тесты на PostgreSQL 18, тесты прав. Те же проверки с этапа 0 выполняет сборочный конвейер на каждый коммит ветки.
5. Провести независимое ревью ветки.
6. Обновить README, этот план и `docs/handoff/`.
7. По команде владельца выкатить на dev-стенд и пройти приёмочный сценарий этапа демо-ролями. Результат записать в `docs/deployment/verification-<дата>.md`.

Без команды владельца ничего не публикуется и не развёртывается.

### 3.2. Готовность среза

- Каждое требование среза закрыто тестом, демонстрацией или обзором (ACC-01); способ записан в карте требований.
- Права проверяет сервер по матрице `packages/contracts/src/policy.ts`. На каждое новое действие есть тест разрешённого и отклонённого запроса (GEN-08, NFR-12). Отказ пишется в аудит.
- Каждое действие пишет запись аудита: кто, организация, время, объект, что изменилось (AUD-01).
- Все пользовательские тексты есть на казахском, русском и английском; наборы ключей совпадают. Исходный язык — английский (LANG-02).
- Миграция совместима с предыдущей версией приложения: expand → migrate → contract (NFR-06).
- OpenAPI соответствует маршрутам.
- В логах и ошибках нет секретов и URL Adata.

### 3.3. Правила данных и интеграций

- **Чтение.** Оператор/наблюдатель и manufacturer exports/pull API читают разрешённые проверенные данные visible verified profiles. Директор видит все профили в каталоге/карточке, но его manufacturer dashboard считает только visible verified. LPS читает собственные сохранённые неудалённые записи без manufacturer verification/NDA.
- **Редакции и история.** Отправленная и верифицированная редакция не перезаписывается. Замена текущих source/DD/draft значений сохраняет полный before/after, автора и время; список названий изменённых полей недостаточен. Оператор читает verified revisions и соответствующие source/file snapshots, без pending values.
- **Коды.** БИН, ОКЭД, ТН ВЭД, КПВЭД, ЕНС ТРУ хранятся текстом (DATA-03). Многозначные поля — отдельными строками (DATA-02).
- **Файлы.** Файл недоступен, пока не прошёл антивирус; отдаётся только после проверки прав записи-владельца (DATA-07, GEN-09).
- **Время.** Даты, сроки и расписания считаются по Asia/Almaty (DATA-08).
- **Внешние сервисы.** Только через коннектор и только из worker. В тестах — заглушка на записанных ответах. Реальный вызов Adata расходует квоту заказчика и делается по прямой команде владельца.
- **Почта.** Автоматические тесты пишут на адреса `.local`; они остаются в Mailpit.

### Этап А. Общий вход — сделан

Требования: AUTH-01–05, AUTH-08–10; MAN-02; NOT-01–03; LANG-01.

Реализовано:

- Вход через OIDC Code + PKCE и BFF-сеанс, пароль остаётся у провайдера идентификации. Все экраны авторизации — собственная тема IMBC на shadcn/ui с переводами kk/ru/en. Стандартные формы Keycloak пользователю не показываются.
- Саморегистрация производителя с проверкой БИН и одним аккаунтом на БИН. Письмо ставится в очередь в той же транзакции. Неудачное удаление пользователя IdP повторяется через `cleanup-identity`.
- Установка и восстановление пароля по почте, ссылка действует 72 часа.
- Шестизначный код на новом устройстве: 10 минут, пять попыток, пауза между отправками. Доверенное устройство хранится 30 дней.
- Принятие ответственности с версией текста. До кода и принятия ответственности рабочие API закрыты.
- Сеанс: 30 минут бездействия, 12 часов от аутентификации. Десять неудачных входов блокируют аккаунт на 15 минут.
- Проверка Origin, ограничения частоты в PostgreSQL, подписанный backchannel logout, отзыв сеансов при смене пароля.
- На dev для демо-аккаунтов действует фиксированный код; порядок — в [runbook](deployment/azure-dev.md#демо-аккаунты-с-фиксированным-кодом).

Автоматические проверки на 10 ноября 2026 года: API — 83 теста, из них 28 интеграционных на PostgreSQL 18; contracts — 23; web — 4. Результаты проверки стенда — в [отчёте от 10.11.2026](deployment/verification-2026-11-10.md).

Критерии приёмки:

1. На настоящем почтовом адресе проходят регистрация → письмо → установка пароля → код → ответственность → стартовая страница роли.
2. Восстановление пароля доступно с экрана входа. Новый пароль работает, старый нет; повторное использование и истечение ссылки дают понятное объяснение.
3. Ошибка почты не теряет регистрацию; письмо остаётся в очереди.
4. Неверный, просроченный, заменённый и использованный код отклоняются. Параллельные запросы не обходят пять попыток и паузу.
5. После смены пароля сеансы и доверие к устройствам на старых учётных данных прекращаются. Отзыв IdP-сеанса закрывает сеансы BFF.
6. Недоступность почты не задерживает отзыв доступа. Неподписанное, чужое, просроченное или повторное уведомление об отзыве не нарушает чужие сеансы.
7. Все шесть ролей проходят вход, выход и повторный вход. Внешний `returnTo` не принимается.
8. Ошибки сети, повторная отправка и смена аккаунта доступны с клавиатуры и на телефоне.
9. Демо-роли проходят вход с фиксированным кодом без письма; аккаунт вне списка получает почтовый код.

### Этап 3. Профиль производителя

**Цель.** Производитель сохраняет семь разделов, отправляет профиль, исправляет возвращённое и меняет Verified через явный Edit. Рабочая разбивка — [3а/3б/3в](superpowers/plans/2026-11-14-stage-3-map.md), текущая детальная часть — [3а v1.4](superpowers/plans/2026-11-16-stage-3a-spec-v1.4.md).

**Требования.** GEN-11; MAN-04, MAN-09–11, MAN-13–15, MAN-17–24, MAN-26–46; DATA-01.

Частичные draft поля и technical edit metadata фиксируются отдельно. Скелет удаляется только после совместимого expand/migrate и contract.

**Работы.**

- 3а: file safety/concurrency и contract этапа 2; модель семи секций; main/contacts save и overview. Юридические данные, учредители и full OKED readonly из Adata, без producer confirmation; missing source не снижает полноту. Editable company phone/email/website и один или несколько sites с address/city/region; stable site identity для products.
- Контакты: минимум три, ровно один focal point, роли могут повторяться, международные номера и нормализованные duplicate email/phone. Второй focal point — немедленная ошибка; верхнего бизнес-лимита нет.

**Приёмка.** Производитель проходит все семь секций, сохраняет неполный draft, видит missing fields и отправляет только при 100%. Source unavailability не требует выдумать юридические сведения. Другой manufacturer не читает/не пишет профиль или файл; submitted/verified content не меняется. Изменение shared site/certificate не раскрывает pending values оператору.

**Перед открытием загрузок:** отдельный 0011; DOCX/XLSX/PDF structure и реальные file corpus; любой /Encrypt PDF и encrypted OOXML отвергаются; причины scan failure; предел process/account с освобождением слотов; dictionary FK и file owner revision. Незавершённые проверки фиксируются в handoff, не объявляются закрытыми по одному unit suite.

### Этап 4а. Внешние источники: копия e-Ondiris, коннектор Adata, каталог проверок

**Цель.** Данные двух источников доступны платформе по БИН, а результат due diligence считается по каталогу проверок. Экраны профиля для этого не нужны, поэтому этап идёт параллельно этапам 1 и 3.

**Требования.** IMBC-10–12, IMBC-14; EXT-01, EXT-02, EXT-04, EXT-05.

**Данные.** `e_ondiris_record`, `external_check`, `external_check_attempt`, `due_diligence_record`, `due_diligence_check`.

**Работы.**

- **Копия e-Ondiris.** Суточное задание забирает новые/изменённые записи с content_hash и сохраняет immutable source snapshots. Поля — текущие MAN-25/DBML; исключённые коды/комментарии и localization не собираются. Verified product ссылается на свой проверенный snapshot, не latest source row.
- **Коннектор Adata.** Задание worker: запрос, опрос раз в 5–10 секунд до 90 секунд. Токен из `ADATA_API_TOKEN`; URL с токеном не попадает в логи. Учёт квоты 3 000 БИН в месяц; запросы идут пакетами с ограничением частоты.
- **Каталог проверок.** Строки функционального каталога IMBC-10 как данные: группа, строка, тип, поле источника. Метки clear, finding, shown only, no answer; отсутствующая строка не создаётся. Результат green, amber или red по IMBC-11 и IMBC-14. Запуск по БИН записывает результат и строки проверки. Части отчёта, которые не являются проверками, не запрашиваются и не хранятся (IMBC-12).
- **Заглушки** остальных коннекторов: четыре случая — green, amber, red, недоступен; результат помечен как тестовые данные.

**Приёмка.** Повторный суточный забор не создаёт дублей и обновляет изменённые записи. Сбой суточного забора, недоступность сервиса и ответ «модуль не подключён» не становятся находкой. На наборе строк из образца отчёта в спецификации результат — amber. Ноль налогов за последний год даёт red. Заглушки показывают четыре случая и помечены как тестовые данные.

**Вводные.** Условия Adata: enabled modules, polling/rate limits и тарификация связанных лиц. Единица квоты по продукту — один логический БИН, не каждый HTTP-вызов. Способ/объём доступа к e-Ondiris уточняется; разовая/еженедельная загрузка без daily update требование не закрывает.

**Вопросы.** Ответы 13 ноября определяют историю DD, видимость и ежедневную частоту; оставшиеся вводные провайдера перечислены выше, старые предложения 12 ноября не применяются.

### Этап 4б. Предзаполнение профиля и запуск due diligence

**Цель.** Profile creation и квартальный запуск используют Adata; daily local e-Ondiris updates сохраняют source history и local producer associations.

**Требования.** MAN-06–08, MAN-12, MAN-25; IMBC-07.

**Данные.** Source attempts/snapshots, main_information/OKED/founders и product rows по DBML; новые immutable revisions и полная before/after история. Нет отдельной таблицы подтверждения каждого юридического поля.

**Работы.**

- Один логический Adata request при создании профиля даёт legal source и DD; квартальный повтор. Брошенная регистрация до profile creation не расходует квоту.
- Adata legal_name/legal_form/director/founders/registered date/legal address/full OKED readonly. Missing/unmatched values сохраняются как source unavailable/issue, без required manual input или manufacturer confirmation.
- Phone/contact email: e-Ondiris, затем Adata, затем producer. Production sites из e-Ondiris prefill editable; producer corrections не стираются. Численность manual.
- Registry summary: registered при хотя бы одном product, earliest inclusion. Нет второго ручного списка OKED; extract attached once products section, diagnostics для IMBC.
- Registry product facts readonly; source name + TN VED duplicate заменяет manual line с сохранением stable identity, site/certificate links; code alone не identity. Active/excluded source records остаются с историей. Pull updates создают revision/snapshot, не перезаписывают submitted/verified.
- DD replacement atomically сохраняет полные before/after current record и ordered checks с shared operation ID; отсутствие модулей/no answer/unavailable не объявляется clean/finding.

**Приёмка.** Profile GET не вызывает сеть/квоту; source refresh не стирает producer contact/site edits и не меняет verified product через latest pointer; full OKED сохраняет leading zeros/unmatched source names; manual duplicate replacement сохраняет identities/associations; старый DD восстанавливается из audit.

**Вводные.** Provider modules/квота/связанные лица, daily e-Ondiris доступ, approved classification/unit aliases. Исторические вопросы 6/11 сняты новой ownership моделью.

**Цель.** SME проводит профиль от отправки до верификации, ведёт записи IMBC; верифицированный профиль попадает в проекцию.

**Требования.** MAN-16; REV-01–09; IMBC-01–03, IMBC-05, IMBC-06, IMBC-08, IMBC-09, IMBC-13, IMBC-15, IMBC-20–24, IMBC-26; EXT-03; NOT-04, NOT-05, NOT-10, NOT-11, NOT-27–29, NOT-34.

**Работы.**

- Очередь Submitted, Under review и Verified с отправленными изменениями; рабочие неотправленные изменения и unlocked profiles вне очереди. Дата — текущий review_assignment.received_at, не registration date. Фильтры по производителю, статусу, исполнителю и дате. SME берёт профиль сам, администратор назначает и переназначает, видя только название, статус и исполнителя.

Tier3 дают report issued/recommendations in progress/recommendation issued; visit/percent/pause сами по себе не дают tier3. Survey request без продукта, AGAR request — этап 9.

**Приёмка.** SME доводит профиль этапа 3 до Verified; возвращённые секции доступны производителю. Два SME не могут взять одну проверку. Непроверенные правки в проекцию не попадают. Результат red держит профиль вне выдачи оператора, пока SME не поставит green или amber. Письмо об обследовании уходит один раз и только по видимому профилю.

**Вопросы.** 14/18/27 разрешены v1.4 и ответами13ноября: DD не открыт оператору, AGAR request в Release 2, SME отвечает на IMBC request. Проверяется реализация.

### Этап 7. Актуальность, уведомления, аудит

**Цель.** Квартальный цикл актуализации, полный каталог писем, журнал и снимки активности.

**Требования.** UPD-01–05; REV-10; NOT-06, NOT-12, NOT-15, NOT-16, NOT-30, NOT-31; LANG-02; AUD-01–04; DATA-08.

**Данные.** `update_status`, `update_confirmation`, `update_status_event`, `certificate_expiry_schedule`, `certificate_expiry_notice`, `activity_snapshot`, `activity_snapshot_count`; `audit_entry` секционируется по месяцам перед продакшеном.

**Работы.**

- Квартал — три календарных месяца от собственной даты профиля. Дата сдвигается подтверждением и принятием изменения SME.
- В дату квартала уходит NOT-12; через семь дней без подтверждения статус outdated. В следующую дату — NOT-15; ещё через семь дней — unresponsive и NOT-16. Verified не снимается, профиль остаётся видимым.
- Не больше 50 писем NOT-12, NOT-15, NOT-16 в день; остальные ждут следующего дня в порядке срока.
- Возврат из unresponsive — подтверждение каждой секции; активным профиль делает последнее.
- Истёкший сертификат переводит active в outdated; замена возвращает active, если причина была только в нём.
- Напоминания 60/30/7/0 дней: новое schedule generation при замене file/date; only current generation dispatch, unique schedule+threshold; expired-on-save не late reminders; null expiry без писем; достижение одним днём группируется по получателю.
- Полный каталог писем: тексты всех писем лежат в языковых файлах, английский — исходный (LANG-02). Общие правила рассылки заведены на этапе 2.
- Аудит: вход, выход, отказы, смены статусов, решения, принятия NDA, выгрузки, скачивания, открытия страниц компаний, LPS CRUD/logical deletion; полные предыдущие значения для восстановления истории. Хранение пять лет, без изменения и удаления.
- Журнал для директора с фильтрами; для администратора — только события аккаунтов. Снимки недели и месяца.

**Приёмка.** Границы семи дней и квартала проверяются управляемым временем. Повтор задания не отправляет второе письмо. Письма сверх 50 уходят на следующий день. Три месяца без входа не двигают квартал.

**Вопросы.** 22 разрешён: certificate schedule generation в текущем DBML; требуется реализация/конкурентная проверка.

### Этап 8. Миграция

**Цель.** Manufacturer workbook/PDFs переносятся и приглашаются; отдельно reconciled LPS workbook становится register data без manufacturer accounts.

**Требования.** ADM-04; NOT-22, NOT-25; MIG-01–16; ACC-03, ACC-07.
