# IMBC: порядок разработки и приёмки

Работу ведём последовательными пользовательскими сценариями: общий вход → минимальное администрирование → производитель → эксперт → оператор → наблюдатель → директор. Каждый следующий этап использует данные и права, подготовленные предыдущим. Общий auth-срез реализован; предметные кабинеты всех ролей ещё не завершены. Этот документ фиксирует объём и критерии приёмки; результаты проверок конкретного развёртывания записываются отдельно.

## 1. Общий вход для всех ролей

В текущем auth-срезе реализованы:

- Вход через OIDC Code + PKCE и BFF-сеанс, пароль остаётся у провайдера идентификации. Все пользовательские экраны авторизации, включая пароль и восстановление, используют собственную тему IMBC на shadcn/ui с переводами kk/ru/en. Keycloak остаётся внутренним сервисом; стандартные формы пользователю не показываются.
- Саморегистрация производителя с проверкой БИН, одним аккаунтом на БИН, черновиком из восьми секций и заданием `send-password-email` в одной транзакции PostgreSQL. Повторная отправка приглашения возвращает нейтральный ответ. Неудачное удаление пользователя IdP после отката повторяется через `cleanup-identity`.
- Установка и восстановление пароля по почте со сроком ссылки 72 часа. На Azure dev Mailpit сохраняет письма и пересылает настоящие адреса через Azure Communication Services SMTP; демо-адреса `.local` остаются в Mailpit. Весь путь на настоящем адресе входит в браузерную приёмку.
- Шестизначный код на новом устройстве: 10 минут, пять попыток, пауза между отправками, состояния доставки и ошибок в интерфейсе. Доверенное устройство хранится 30 дней.
- На dev для шести seed-аккаунтов и отдельного `test-admin@imbc.local` используется `000000` без письма. `DEV_FIXED_OTP_ACCOUNTS` задаёт точные пары UUID и ожидаемой роли, по умолчанию список пуст; legacy `DEV_FIXED_OTP_USER_ID` сохраняется для отдельного администратора. Исключение требует включённого флага и `DEPLOYMENT_ENV=development`, проверяется при выдаче и вводе кода, не зависит от email или `.local`. Обычные пользователи получают случайный почтовый код. Пароли, права ролей, ответственность и ограничения OTP сохраняются. [Список аккаунтов и отключение](deployment/azure-dev.md#демо-аккаунты-с-фиксированным-кодом).
- Принятие ответственности с версией текста; до прохождения кода и принятия ответственности рабочие API закрыты.
- Сеанс с ограничением бездействия 30 минут и абсолютным сроком 12 часов от аутентификации, выход с подтверждением без автоматического повторного входа, безопасный возврат и стартовая страница по роли. Производитель открывает `/profile`, администратор — `/account`, остальные роли — `/catalog`.
- Проверка Origin для изменяющих запросов, ограничения частоты запросов в PostgreSQL, подписанный backchannel logout с защитой от повторного создания отозванного сеанса, обработка событий изменения пароля до отправки уведомлений.

Автоматические проверки этого среза на 10 ноября 2026 года: API — 83 теста, в том числе 28 интеграционных на PostgreSQL 18; contracts — 23; web — 4. Проверены список UUID и ролей для фиксированного OTP, обычная почтовая доставка вне списка и отзыв ещё не использованных тестовых кодов при изменении разрешений. Эти результаты проверяют код и не заменяют следующие сценарии приёмки развёрнутого приложения. Условия запуска интеграционных тестов — в разделе 14 README, результаты проверки стенда — в [отчёте от 10.11.2026](deployment/verification-2026-11-10.md).

Критерии приёмки общего auth-среза:

1. На настоящем почтовом адресе проходят регистрация → письмо → установка пароля → код → ответственность → разрешённая стартовая страница.
2. Восстановление пароля доступно с экрана входа. Новый пароль работает, старый не работает; повторное использование и истечение ссылки дают понятное объяснение и путь восстановления.
3. Ошибка почты не теряет регистрацию; письмо остаётся в очереди и может быть отправлено повторно. Пользователь видит состояние запроса без утверждения, что письмо уже доставлено в его ящик.
4. Неверный, просроченный, заменённый и уже использованный OTP отклоняются. Параллельные запросы не обходят пять попыток и паузу между отправками.
5. После смены пароля сеансы и доверие к устройствам, основанные на старых учётных данных, прекращают действовать. Отзыв IdP-сеанса закрывает соответствующие сеансы BFF. Новый законный вход сохраняется. Проверяется пересечение этих событий с уже выполняющимися входом и проверкой кода.
6. Недоступность почты не задерживает отзыв доступа. Неподписанное, чужое, просроченное или повторное уведомление об отзыве не может нарушить сеансы других пользователей.
7. Все шесть ролей проходят вход, выход и повторный вход; истечение сеанса и запреты прямых API-запросов действуют одинаково для каждой роли. Внешний `returnTo` не принимается.
8. Ошибки сети, повторная отправка и смена аккаунта доступны с клавиатуры и на телефоне. В интерфейсе нет названий внутренних требований и технических заглушек.
9. Все шесть демо-ролей и отдельный тестовый администратор проходят пароль → `000000` → ответственность → разрешённую стартовую страницу без отправки OTP-письма. Аккаунт вне разрешённого списка использует случайный почтовый код. Удаление пары из списка, выключение исключения или несовпадение роли отклоняет ещё не использованный фиксированный код; проверяются срок действия, лимит попыток и повторное использование. Возможность ввода `000000` не даёт роли дополнительных прав.

## 2. Минимальное администрирование и жизненный цикл аккаунта

Это следующий этап после общего входа. Наличие страницы `/account` и проверки `auth_version` ещё не означает готовность административного кабинета. Автоматическая неактивность AUTH-07 пока не реализована: задание `account-inactivity` запускается по расписанию с обработчиком-заглушкой. Отказ входа уже неактивному аккаунту и обработка смены пароля сами по себе не завершают AUTH-07.

Работы:

- Список организаций и аккаунтов, приглашения экспертов, администраторов, директора, операторов и наблюдателей; повторная отправка приглашений.
- Блокировка, разблокировка, изменение разрешённой роли и немедленный отзыв активных сеансов через `auth_version` и провайдера идентификации.
- AUTH-07: предупреждение о приближающейся неактивности, переход в `inactive` после трёх месяцев без входа, обязательное восстановление пароля и возврат к работе. Расписание учитывает `Asia/Almaty`; связанные подписки приостанавливаются.
- Журнал действий с аккаунтами, доступный администратору в пределах его полномочий.

Приёмка: администратор приглашает пользователя нужной организации и роли, пользователь активирует доступ по письму; блокировка и смена роли действуют на уже открытые сеансы. Повторное выполнение задания не создаёт второе приглашение или уведомление. Даты до и после границ трёх месяцев проверяются управляемым временем. Администратор управляет аккаунтами, но не получает доступ к содержимому профилей и записям IMBC.

## 3. Производитель

Работы: восемь секций — основные сведения, контакты, персонал, акционеры, продукты, производство, сертификаты, документы; сохранение редакций, полнота, отправка на проверку и исправления после возврата. Файлы проходят карантин, проверку типа и антивирус; скачивание требует прав на запись-владельца. Предзаполнение продуктов из e-Öndiris сохраняет ручной ввод при недоступности источника.

Приёмка: производитель заполняет профиль, загружает документы, видит ошибки у соответствующих полей, отправляет данные и получает замечания по секциям. После принятия изменений видит различие между рабочими, ожидающими и верифицированными значениями. Аккаунт одной компании не может прочитать или изменить профиль другой компании через UI или API.

## 4. Эксперт IMBC

Работы: очередь проверки, назначение и принятие в работу, решения по секциям и документам, возврат с причиной, разблокировка проверки, обработка изменений проверенного профиля. Затем записи обследований, due diligence и остальные записи IMBC; реальный адаптер Adata подключается по согласованному контракту.

Приёмка: эксперт проводит полученный на предыдущем этапе профиль от отправки до верификации; возвращённые секции доступны производителю для исправления. Эксперт выносит решения, сохраняя введённые производителем значения. `catalog_visible` обновляется согласованно с решением; непроверенные правки не попадают в выдачу оператора. Два эксперта не могут одновременно присвоить одну проверку себе.

## 5. Оператор

Работы: каталог и справочники фильтров, страница компании и PDF, документы, дашборд; отметки сотрудничества и визитов, заметки своей организации, запросы IMBC и производителю. Затем стандартные выгрузки и pull API только для чтения с ключом организации.

Приёмка: оператор находит верифицированную компанию, передаёт ссылку с фильтрами, читает разрешённые документы и оставляет запись своей организации. Невидимые профили, непроверенные правки, записи IMBC и записи другой организации недоступны в интерфейсе, файлах, выгрузках и прямых API-запросах. Истечение сертификата и изменение актуальности учитываются по согласованным правилам.

## 6. Наблюдатель

Работы: законченный режим чтения каталога, страницы компании, файлов, PDF и дашборда на основе готового операторского сценария.

Приёмка: наблюдатель читает разрешённые видимые профили; изменения данных, выгрузки, подписки, pull API и служебные записи отклоняются на сервере. Отсутствие кнопки проверяется вместе с запретом соответствующего прямого запроса.

## 7. Директор IMBC

Работы: чтение профилей и записей, разрешённых директору, дашборд, выгрузки и полный журнал аудита с фильтрами по пользователю, организации, объекту, действию и времени.

Приёмка: директор видит положенную ему информацию из завершённых сценариев производителя, эксперта и оператора; изменения профильных данных и административные операции ему недоступны. Изменения состояния, отказы доступа и чтение компании отражаются в журнале с нужным контекстом.

## Последующие сквозные этапы

После проверки основных ролей идут квартальная актуализация и полный каталог уведомлений, миграция Excel/PDF, приёмка Release 1. Прогноз спроса, NDA и подписки проходят отдельный цикл Release 2. Для передачи среды в эксплуатацию отдельно проверяются нагрузка, восстановление резервных копий, наблюдаемость и процедуры обновления.

Расширение функций не меняет общие правила: один источник прав для UI и API, проверка прав на каждом объекте, закрытые файлы, аудит и согласованные русские, казахские и английские тексты.
